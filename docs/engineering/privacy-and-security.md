# 隐私与安全基线

状态：工程原型当前实现与待补控制（2026-09-21）。本项目只用于面试演示，不接入真实患者系统，也不宣称通过医疗器械或隐私合规认证。

## 当前已实现

- 仓库只分发来源、许可已登记的样例：合成 PNG、公开 CC BY 4.0 心脏参考 STL；默认 DICOM 由 seed 生成无患者来源的 phantom。可选外部 DICOM 仅在本地生成清理副本后使用，原始文件不进 Git。
- API 根据扩展名、DICOM 魔数及解析器结果判型，限制上传大小；文件以随机 UUID 名保存，**不持久化原始文件名**，也不在默认响应或日志中输出它。
- DICOM 仅从显式 [白名单](../design/dicom-metadata-whitelist.md)生成 `metadata_summary`；患者姓名、患者 ID、自由文本描述及完整标签转储不进入响应。像素不可用时只给降级警告。
- 对外错误返回稳定错误码、`next_action` 与 `request_id`，不返回堆栈。访问日志记录 `request_id`、方法、路径、HTTP 状态和耗时；错误路径可附 `error_code`。日志扫描验证已知敏感模式零命中，见 [P8 证据](../product/12-p8-test-report.md)。
- 数据库、上传文件、预览、运行日志、`.env`、虚拟环境及题目附带的 DICOM/STL 不进入 Git。测试栈与演示栈隔离。

## 当前边界与仍需补齐

- 逐素材来源 URL、许可和“已脱敏/未核验”等结构化状态**尚未入库**；界面只显示服务端通用 `source_label`，仓库样例的详细来源与清理状态另记于 [样例登记](../../sample-data/README.md)。不能把这份文档登记当作业务系统中的逐素材溯源。
- DICOM 清理脚本不是临床级去标识化流程；它不证明像素里没有烧录文字。演示前必须人工检查内容，不使用真实患者数据。
- 当前没有真实登录、服务端授权矩阵或持久化 `audit_events` 表。`request_id` 访问日志与追加式评审历史能帮助工程排障，**不等于**合规业务审计；审计日志与运行日志分离是未来目标。
- 数据库提交失败后的上传文件可能残留；未评审素材删除路径先删文件再提交 DB，失败时可能不一致。此风险在 [技术设计](../../TECH_DESIGN.md)明示，尚未实现事务性补偿。
- 文件内容校验不等同于恶意文件隔离或临床可靠性评估。真实机构使用前仍需身份认证、最小权限、审计、防篡改、加密、数据保留策略、专业去标识化和安全测试；见 [真实医疗软件能力差距](real-world-readiness.md)。
