# PRD：结构性心脏病术前规划素材评审工作台

状态：Approved for P1  
版本：1.1  
更新时间：2026-09-20

## 1. 背景与问题

术前讨论前，病例的 CT/DICOM、标注图片和 3D 分割模型常散落在网盘、本地目录或临时沟通记录中。版本混乱、素材能否加载不清楚、评审意见难以沉淀，导致术前规划工程师和影像技术评审员在讨论前反复确认素材状态。

本产品解决的是“素材准备与工程评审”问题，而不是临床诊断问题。

## 2. 产品定位

一句话：面向结构性心脏病术前规划的素材评审工作台。

是什么：把同一病例的 DICOM、图片和 3D 解剖模型聚合到病例上下文中，完成验证、状态标记和结论沉淀。

不是什么：不是阅片器，不做诊断结论，不给治疗建议，不接真实患者系统。

## 3. 目标用户

- 主要用户：术前规划工程师，负责汇总、验证、标记素材。
- 次要用户：影像技术评审员，负责复核素材并留下工程评审结论。

## 4. 用户故事

作为术前规划工程师，我希望在讨论前把同一病例的 DICOM 序列/单文件、图片和 3D 模型汇总到一个病例下，逐条验证并留下结论，以便团队讨论时素材状态和评审依据可追溯。

## 5. 核心流程

创建项目 → 创建脱敏病例 → 关联素材 → 浏览/筛选/比较/整理 → 逐条验证 → 标记状态 → 保存评审结论 → 重新打开可追溯。

## 6. 产品思维约束

所有功能必须通过四项检查：

| 检查项 | 本项目中的回答 |
|---|---|
| 先问为什么 | 解决术前讨论前素材散落、不可验证、结论不可追溯的问题 |
| 定义边界 | 做素材评审与结论沉淀，不做临床诊断、治疗建议、完整阅片 |
| 排优先级 | 图片浏览/筛选/比较/整理属于题目明确要求并进入核心闭环；AI 草稿等增强能力延后 |
| 可验证 | 用 `DEMO-TAVR-001` 走通五分钟演示流程 |

## 7. 功能需求

| ID | 需求 | 解决的痛点 | 优先级 |
|---|---|---|---|
| FR-001 | 用户可以创建项目和脱敏病例编号 | 同一病例素材缺少上下文 | Must |
| FR-002 | 用户可以关联 DICOM、图片和 STL 素材，并记录来源 | 素材散落、来源不清 | Must；当前仅有通用类别标签，逐素材来源/许可/脱敏状态尚未落库 |
| FR-003 | 系统生成素材 UUID、大小、哈希和基础格式识别结果 | 文件版本和完整性不可追溯 | Must |
| FR-004 | 素材卡片展示格式、来源、标签、状态和备注 | 讨论前不知道素材准备到哪一步 | Must |
| FR-005 | DICOM 展示安全元数据、缩略图和多帧信息 | DICOM 能否用于演示不清楚 | Must |
| FR-006 | 3D 模型支持旋转、缩放、平移、复位和结构标记 | STL 是否可查看、结构是否可辨认不清楚 | Must |
| FR-007 | 用户可以保存评审结论：状态、文本、时间、评审人、问题摘要、下一步 | 结论靠口头传递，无法沉淀 | Must；当前保存 decision/note/reviewer_name/created_at，问题摘要与下一步未拆成独立字段 |
| FR-008 | 用户可以按类型、状态和标签筛选素材 | 多素材下定位问题效率低 | Must |
| FR-009 | 用户可以浏览图片缩略图、选择两张并排比较，并通过标签、状态和备注整理图片 | 标注图或截图需要对照，整理结果需要沉淀 | Must |
| FR-010 | 系统对缺失、损坏、格式不支持、加载失败、保存失败给出明确错误和 `request_id` | 异常不可解释，难以排查 | Must |
| FR-011 | 系统记录结构化日志，但不得输出患者姓名、患者 ID、请求正文或原始文件名 | 工程排障与隐私保护需要兼顾 | Must |

## 8. 评审结论定义

下表是 P1 产品目标；实际 API 与数据库字段以 [技术设计](../../TECH_DESIGN.md)和运行时 OpenAPI 为准。当前 `decision` 映射到素材状态（`accept→accepted`、`needs_changes→needs_changes`、`reject→rejected`），`note` 可合并承载结论/问题/下一步，`reviewer_name` 记录评审人，`created_at` 为保存时间。**当前 `note` 可为空**，因此“必填文本结论”目标尚未完全满足。`issue_summary`、`next_action`、独立 `reviewed_at` 尚未实现；错误信封的 `next_action` 不是业务评审下一步。

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `status` | enum | 是 | 待评审、可用、需补充、不可用 |
| `conclusion_text` | text | 是 | 人工评审结论 |
| `reviewer` | string | 是 | 演示角色或评审人 |
| `reviewed_at` | datetime | 是 | UTC ISO 8601 |
| `issue_summary` | text | 否 | 问题摘要 |
| `next_action` | text | 否 | 下一步处理建议 |

## 9. 非功能需求

| ID | 需求 |
|---|---|
| NFR-001 | 默认本地运行，不依赖外部 API Key |
| NFR-002 | 开发期使用 SQLite，生产说明可切换 PostgreSQL |
| NFR-003 | 上传文件、数据库、日志和生成预览不进入 Git |
| NFR-004 | 所有错误返回稳定错误码和 `request_id` |
| NFR-005 | 日志禁止输出患者姓名、患者 ID、请求正文、原始文件名和完整 DICOM 标签 |
| NFR-006 | DICOM 元数据只展示白名单字段 |
| NFR-007 | 项目必须支持自动化安装、检查、测试和生产构建 |

## 10. 样例数据

公开仓库默认提交两张合成 PNG 和有 CC BY 4.0 署名的心脏参考 STL；全新克隆的 seed 在运行时生成非临床 DICOM phantom。下表中的其他外部 DICOM/STL 是**开发者本地可选样例**，不是面试官克隆后必然拥有的文件。

| 素材 | 路径 | 用途 | 当前状态 |
|---|---|---|---|
| 运行时 DICOM phantom | seed 确定性生成 | 默认 DICOM 解析、白名单元数据和缩略图链路 | 全新克隆可用；非临床 |
| 心脏参考 STL | `sample-data/stl/vh-f-heart.stl` | 默认 3D 查看与结构标记 | 全新克隆可用；来源与 CC BY 4.0 署名见 `sample-data/stl/ATTRIBUTION.md`；并非演示 DICOM 的病例重建 |
| 运行时 STL 曲管 | seed 确定性生成 | 仅在心脏参考 STL 缺失时回退 | 非真实解剖 |
| pydicom 清理副本 | `sample-data/dicom/CT_small_anonymized.dcm` | 进阶 DICOM 验证 | 本地可选，不入 Git |
| Rubo 清理副本 | `sample-data/dicom/rubo_angiogram_0002/0002_anonymized.DCM` | 96 帧单文件演示 | 本地可选，不入 Git |
| 题目 STL | `sample-data/stl/{aorta,CB,LA,LVOT}.stl` | 题目模型和加载压力演示 | 本地可选，不入 Git |
| 合成 PNG/标注图 | `sample-data/image/synthetic-cardiac-ct-*.png` | 图片浏览、筛选、并排比较、整理和结论沉淀 | 已生成；可提交的非临床合成素材 |

## 11. 明确不做

- 临床阅片。
- 诊断结论。
- 治疗建议。
- 真实患者数据。
- 完整 PACS/阅片器。
- 自动分割、模型训练、空间配准、手术导航。
- 多人实时协同和复杂权限。
- 产品内真实 AI 接入，以及由 AI 自动作出临床可用性、诊断或治疗决策。

## 12. 成功指标

- 五分钟内完成一次 `DEMO-TAVR-001` 素材评审演示。
- 正常 DICOM 和 STL 可以被识别、查看并保存评审结论。
- 两张合成图片可以浏览、筛选、并排比较、整理并保存评审结论。
- Rubo DICOM 被识别为多帧单文件。
- 异常素材不会拖垮应用，并给出错误码、下一步和 `request_id`。
- 刷新或重启后评审结论不丢失。
- 日志扫描未发现患者姓名、患者 ID、请求正文或原始文件名。

## 13. 发布门禁

- 主流程和至少三条异常流程有测试或可复现证据。
- PRD、验收矩阵、README 和实际行为一致。
- 演示数据来源、许可、日期、用途和哈希记录完整。
- AI 使用记录包含验证方法和至少一条被修改或拒绝的建议。
- 真实医疗场景所需权限、审计、隐私合规、脱敏和协作能力有明确差距说明。

## 14. P4/P5 可执行状态映射

为避免产品文档与 API 枚举漂移，当前实现统一使用以下状态：

| 产品含义 | API/前端值 |
|---|---|
| 待评审 | `pending` |
| 可用/通过 | `accepted`（评审请求为 `accept`） |
| 需补充 | `needs_changes` |
| 不可用/拒绝 | `rejected`（评审请求为 `reject`） |

旧版文档中的“可用/不可用”是产品语义，不再作为接口原始枚举；前端展示使用中文标签，服务端保存稳定英文值。
