# P1 问题收口

文档状态：Approved  
更新时间：2026-09-20

## 已确认

| 问题 | 结论 |
|---|---|
| Q1：首要用户是谁？ | 术前规划工程师 |
| Q2：次要用户是谁？ | 影像技术评审员 |
| Q3：最痛的问题是什么？ | 术前讨论前，同一病例的 CT/DICOM、图片和 3D 模型散落，版本混乱，评审结论不可追溯 |
| Q4：核心任务何时算完成？ | 同一脱敏病例下的素材完成验证，每条素材都有状态、结论、时间和评审人 |
| Q5：本次 MVP 定位是什么？ | 结构性心脏病术前规划素材评审工作台 |
| Q6：是否做临床诊断或治疗建议？ | 不做 |
| Q7：DICOM 首期怎么处理？ | 支持单文件 DICOM；Rubo 样本按多帧单文件处理，不按目录序列处理 |
| Q8：图片是否阻塞 MVP？ | 阻塞。题目明确要求图片浏览、筛选、比较、整理和结论沉淀，已提升为 Must，并准备两张非临床合成 PNG |
| Q9：是否使用真实患者数据？ | 不使用，只用公开、去标识化或演示数据 |
| Q10：是否接入真实 AI？ | 当前不接入产品内真实 AI；研发 AI 输出必须人工验证，产品内 AI 决策明确属于 Out |

## 后续阶段注意

- P2 技术设计必须把“评审结论字段”落成数据模型和 API 契约。
- P2 技术设计必须评审并确认 `docs/design/dicom-metadata-whitelist.md` 中的 DICOM 白名单字段。
- P3 脚手架必须先实现健康检查、request ID 和基础日志，再进入业务实现。
- P4/P5 必须优先打通“病例素材评审闭环”，不要先做锦上添花的 UI。
